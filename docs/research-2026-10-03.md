# Standards and provider research

**Checked:** 3 October 2026.
**Purpose:** evidence for the [implementation plan](implementation-plan.md).
**Method:** initial planning research used primary specifications, host/provider documentation, the official MCP SDK repository, and public OpenRouter discovery. The baseline sections below preserve findings at that stage; implementation verification is recorded separately.

## Implementation follow-up

The four adapters and 11-model catalogue now have 33 successful live workflow records plus visual review. Muse uses the dedicated Images API; its initially empty discovery metadata did not prevent successful generation, reference composition, or editing. Gemini uses stable v1 Interactions with the `user_input` envelope and no `delivery` option. Nullable/mixed Replicate result metadata is handled, and an existing prediction was recovered without another submission. See [model evidence](model-catalogue.md) and the [validation report](validation.md) for the current result and remaining host/OS limitations.

Dependencies are pinned to MCP server/client 2.3.0, Zod 4.6.5, Sharp 0.35.5, TypeScript 7.0.2, and esbuild 0.28.2. Local execution used Node 24.19.0. Modern and legacy stdio were exercised through real client/server subprocesses. The statements below about unverified runtime work describe the earlier research phase, not the current implementation.

This is a dated evidence baseline. It does not certify behavior for later October releases, account-specific access, or every model available from an aggregator.

## Credential setup follow-up

Claude's `userConfig` supports masked sensitive fields with platform secure storage, but that is host-owned configuration. OpenAI's plugin guidance explicitly requires replacing Claude `userConfig`; the portable specification does not define a shared install-time secret prompt. The user chose one set of keys across hosts, so this plugin provides a terminal wizard and retrieves its own OS-stored entries in the MCP process. [Claude configuration](https://code.claude.com/docs/en/plugins-reference#user-configuration), [OpenAI migration guidance](https://developers.openai.com/plugins/guides/submit-claude-plugin#replace-claude-userconfig), [portable environment contract](https://agent-plugins.org/specification#9-environment-variables-and-placeholder-expansion).

The implementation pins `@napi-rs/keyring` 2.1.0 and `@inquirer/prompts` 8.7.2. The keyring library defaults to a Linux keyutils fallback when Secret Service is unavailable; keyutils does not persist through reboot. The plugin explicitly selects Secret Service so a successful save has durable storage. Its adapter normalizes an observed Windows `null` for a missing entry despite the asynchronous TypeScript declaration saying `undefined`. Real Windows storage, cross-process retrieval, and deletion were checked with a synthetic isolated entry. [Keyring library](https://github.com/Brooooooklyn/keyring-node), [Inquirer](https://github.com/SBoudrias/Inquirer.js).

## GitHub installation follow-up

Codex accepts GitHub marketplace sources and the installed 0.160.0 CLI provides `plugin add`. Claude supports a GitHub marketplace containing a relative plugin entry. OpenCode v2 accepts Git package specifications; its native plugin API can register an MCP server and skill through transforms. The 2.0.18 installed host discovered this adapter through the root `index.js` package entry and connected its MCP server. [Codex marketplace guide](https://developers.openai.com/plugins/build/plugins#add-a-marketplace-from-the-cli), [Claude marketplace guide](https://code.claude.com/docs/en/plugin-marketplaces), [OpenCode Git installation](https://opencode.ai/v2/docs/plugins/#manage), [OpenCode plugin API](https://opencode.ai/v2/docs/build/plugins).

The Agent Plugins specification explicitly permits installed dependencies and generated code in `PLUGIN_DATA`. The source bootstrap installs pinned production dependencies there and runs a copied source tree using Node 24 type stripping. Node refuses to strip TypeScript under `node_modules`, which is why the runtime uses the data directory even when a host installs the plugin as an npm-compatible Git package. [Portable environment contract](https://agent-plugins.org/specification#9-environment-variables-and-placeholder-expansion), [Node TypeScript support](https://nodejs.org/api/typescript.html).

## Packaging and host baseline

| Area | Verified documentation finding | Design implication |
| --- | --- | --- |
| Agent Plugins | Published version 1.0.0 uses root `plugin.json`; skills and MCP configuration have fixed locations. [Specification](https://agent-plugins.org/specification) | Make this the canonical portable package. |
| Portable MCP | Root `mcp.json` carries its own matching schema and explicit transport types. [Author guide](https://agent-plugins.org/plugin-authors/mcp-servers) | Native `.mcp.json` files need translation; renaming is insufficient. |
| Agent Skills | `SKILL.md` has required name/description metadata and progressive disclosure of supporting material. [Specification](https://agentskills.io/specification) | Share concise workflow instructions; keep detailed provider references separate. |
| Codex | Current packaging docs accept the portable layout and `extensions.com.openai`. [Package guide](https://developers.openai.com/plugins/build/plugins) | Use the root package for current Codex; add native compatibility packaging only for a justified target version. |
| Claude Code | Documented manifest location is `.claude-plugin/plugin.json`; native MCP configuration and plugin data variables are host-specific. [Manifest reference](https://code.claude.com/docs/en/plugins-reference) | Produce and validate a Claude release layout from shared sources. |
| OpenCode v2 | Local MCP servers live under `mcp.servers`; protocol mode defaults to legacy. [MCP guide](https://opencode.ai/v2/docs/mcp-servers) | Test v2 explicitly and label v1 recipes separately. |
| OpenCode skills | v2 discovers local skills and supports configured skill sources. [Skills guide](https://opencode.ai/v2/docs/skills) | Ship a documented MCP-plus-skills integration; a native event-hook plugin is optional. |

The standard's [compatible-client directory](https://agent-plugins.org/compatible-clients) lists Codex, but does not list Claude Code or OpenCode on the inspection date. Absence is not proof of non-support. Their own documented formats provide the defensible integration path until runtime tests establish more.

Portable processes receive `PLUGIN_ROOT` and persistent `PLUGIN_DATA`. The standard permits a sanitized ambient environment and only defines expansion for those two variables. This makes arbitrary API-key interpolation or inherited shell credentials an invalid portability assumption. The default subprocess working directory is the plugin root. [Environment and path requirements](https://agent-plugins.org/specification)

OpenAI's public submission path asks local MCP authors to deploy a remote HTTPS endpoint or contact OpenAI about local MCP support. This is a public-directory constraint, separate from local Codex operation. [Bundled MCP and submission guidance](https://developers.openai.com/plugins/build/plugins#bundled-mcp-servers-and-lifecycle-hooks)

## MCP revision and SDK baseline

The current specification resolves to **2026-07-28**. It removes the old initialization handshake in favor of discovery and per-request metadata, and moves redesigned Tasks into an extension. Designing solely around the 2025 handshake or experimental 2025 Tasks would miss these changes. [Current specification](https://modelcontextprotocol.io/specification/2026-07-28), [revision changes](https://modelcontextprotocol.io/specification/2026-07-28/changelog)

The official TypeScript SDK describes v2 as its stable release line. Server and client packages are split. The SDK's versioned guidance says `serveStdio` supports modern and legacy connections; directly wiring `McpServer` to `StdioServerTransport` still uses the older protocol family. [SDK repository](https://github.com/modelcontextprotocol/typescript-sdk), [protocol migration guide](https://ts.sdk.modelcontextprotocol.io/v2/migration/support-2026-07-28), [legacy-client guide](https://ts.sdk.modelcontextprotocol.io/v2/serving/legacy-clients)

The current Tasks extension uses durable handles and polling, with cooperative cancellation. It requires negotiated support. Ordinary job tools remain a proposed compatibility path for hosts that lack the extension. [Tasks overview](https://modelcontextprotocol.io/extensions/tasks/overview)

Exact npm versions and each host's negotiated protocol remain unverified. The general SDK documentation link initially opened v1 documentation; the explicit `/v2/` documentation and official repository were used to resolve the release-line distinction. The standalone current MCP tools-spec page could not be retrieved, so detailed tool-schema implementation must be checked against the SDK and versioned schema during the first milestone.

## Provider baseline

| Provider | Current verified interface | Consequence for this project |
| --- | --- | --- |
| OpenAI | The image guide documents `gpt-image-2.5-sunburst` and `gpt-image-2.5-flare`, generation/edit endpoints, and Responses image tools. [Image generation guide](https://developers.openai.com/api/docs/guides/image-generation) | Candidate direct models; prefer Images for individual host-directed actions. |
| Gemini | The Interactions API is documented as generally available since June 2026 and recommended for new projects; `generateContent` remains supported. [Interactions overview](https://ai.google.dev/gemini-api/docs/interactions-overview) | Build against the current interface and explicitly choose state/storage behavior. |
| Gemini image models | Current image guidance lists `gemini-3.1-flash-image`, `gemini-3.1-flash-lite-image`, `gemini-3-pro-image`, and `gemini-2.5-flash-image`. [Image guide](https://ai.google.dev/gemini-api/docs/image-generation) | Model capabilities need separate descriptors, especially reference and editing behavior. |
| Replicate | Models expose their own input/output OpenAPI schemas. [Schema reference](https://replicate.com/docs/reference/openapi/) | A generic model name plus prompt cannot express every model correctly. |
| Replicate lifecycle | Async prediction creation is the default; a synchronous wait can end before the prediction completes. [Prediction creation](https://replicate.com/docs/topics/predictions/create-a-prediction) | Retain IDs and recover by polling; a wait timeout is not a failed generation. |
| OpenRouter | A dedicated Images API supports model and per-endpoint capability discovery. [Image generation guide](https://openrouter.ai/docs/guides/overview/multimodal/image-generation) | Implement this route explicitly rather than assuming every image model uses chat completions. |

OpenAI documents image quality, format, transparency, reference editing, and masks. Those controls should be exposed only for matching model/API capabilities. API model access may require organization verification; a configured key alone does not prove access. [OpenAI image guide](https://developers.openai.com/api/docs/guides/image-generation)

Gemini's image guide uses Interactions and warns that the convenience image property returns the last image block rather than every image in an interleaved response. It also documents SynthID watermarking. Its legacy Imagen page now says Imagen is shut down in the Gemini API. [Image output guidance](https://ai.google.dev/gemini-api/docs/image-generation), [Imagen status](https://ai.google.dev/gemini-api/docs/imagen)

Gemini Interactions stores requests by default. `store=false` prevents later continuation through `previous_interaction_id` and cannot be combined with background execution. This is a product decision about persistence and recovery, not an incidental SDK default. [Interactions storage](https://ai.google.dev/gemini-api/docs/interactions-overview#data-storage-and-retention)

Replicate API output files are deleted after an hour. Persisting local files is required for the promised durable-asset workflow. [Output files](https://replicate.com/docs/topics/predictions/output-files)

OpenRouter documents `GET /api/v1/images/models`, per-endpoint records, and `POST /api/v1/images`. Endpoint records specify supported controls, passthrough keys, streaming, and pricing. Model-level support is a union; endpoint records determine whether a concrete route can satisfy a request. [Image API guide](https://openrouter.ai/docs/guides/overview/multimodal/image-generation), [image-model endpoint](https://openrouter.ai/docs/api/api-reference/images/list-image-models)

## Evidence limits and next verification

The user confirmed a tested catalogue for the main labs plus Qwen and Muse. The [dated catalogue](model-catalogue.md) records the proposed 11-model shortlist, provider mappings, public endpoint observations, and operation-level validation criteria. The supplied [portrait benchmark](https://openrouter.ai/benchmarks/media/images/portraits?variant=studio-headshot) informed model discovery; it does not establish our plugin's compatibility or a universal quality ranking.

Replicate documents generation and reference editing for [FLUX 3 Image](https://replicate.com/black-forest-labs/flux-3-image), making it the proposed first Replicate target. On 3 October, OpenRouter's dedicated Image API returned endpoints for the other shortlist entries but none for `meta/muse-image`. Its general model endpoint returned a Meta route, while its model page described reference editing. These are different pieces of evidence; Muse's usable route and operation support remain unverified. [Image endpoint response](https://openrouter.ai/api/v1/images/models/meta/muse-image/endpoints), [general endpoint response](https://openrouter.ai/api/v1/models/meta/muse-image/endpoints), [Muse description](https://openrouter.ai/meta/muse-image-1.0-eval-20260824)

- No live generation, provider billing, credential validation, model quality comparison, or host installation was performed.
- Model IDs above are documented candidates. Final defaults require account access and workflow tests; no universal quality ranking is claimed.
- Exact SDK/runtime versions, minimum host versions, inline image rendering, and OS credential-store behavior belong in the first compatibility milestone.
- FLUX 3's exact executed version/schema and Muse's API contract require implementation-time verification. Muse remains requested scope; an empty dedicated endpoint list does not establish global unavailability.
- Package conformance, host support, provider availability, and public marketplace eligibility are separate claims and must be tested or documented separately.
